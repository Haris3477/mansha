## What Mansha is
An AI agent that tells a UAE exporter whether a product qualifies for reduced or zero customs duty under a UAE CEPA, proves it with the agreement's own rules, and lists the steps to claim it. Name: Arabic منشأ ("origin"), the word on a certificate of origin (شهادة منشأ). Primary direction: UAE exporters selling OUT to partner countries; first corridor UAE → India.

Decided 13 Oct 2026: this replaces the earlier business-licensing idea (SafeAgent UAE), because licensing is already well served by official AI assistants (e.g. TAMM's), while origin qualification for SMEs is not. The backend, LLM client and lessons carry over; licensing-specific code does not.

**Scope clarification (14 Oct 2026):** the demo products are TEST CASES that prove each branch works (qualifies / fails / needs data / excluded), not the scope. All tools and agents are generic (no product-specific code or prompts). Coverage is limited only by the data loaded; a line not in the knowledge base → a "not covered" answer or REGULATORY_GAP_DETECTED, never a guess. The hard part for "any product" is classification (description → 8-digit line), solved properly in roadmap milestone 5 (milestone 4 before the 20 Oct renumbering) (full Table I + better search).

**Positioning (Haris, 20 Oct 03:00, option A; details in roadmap.md "Positioning"):** Mansha is the **SME pre-check for UAE → India CEPA origin**: a UAE manufacturer without a compliance team learns whether a product qualifies, sees the proof, and gets a broker-ready report or an honest "can't conclude yet". It complements brokers and the chamber's certificate service, not enterprise trade-management software. Verified 20 Oct: AI origin qualification is an existing category (Descartes FTI launched 4 Aug 2026 with BOM analysis, value-content and tariff-shift logic, supplier declarations, audit trail and scenarios; Altana; Tijara; ITC's free SME facilitator), so we never claim "first" or "only". Option B (broker/chamber copilot) is the fallback if interviews show brokers need it more; option C (sourcing "what would make it qualify" advisor) not chosen (overlaps Descartes, needs real costs, conflicts with the privacy rule). Validation interviews (roadmap milestone 3) now run in parallel with the build.

## Step 7 as built (17–19 Oct 2026)

### Design decisions (7.1, agreed with Haris)
- **D1 — what QA judges (meaning only; code checks form):** factuality (tariff line justified by its description; each basis/step/caveat says what its cited record says: no merged facts, no reversed or stronger meaning, qualifiers kept; each code warning REAL or NOISE); completeness ("what's still needed" only asks for things the user hasn't given and that can change the result; every failed check named; no caveat that clearly doesn't apply); formatting_safety (no field names, code values, prompt text, suppliers, costs). Calibration sentence against false rejections ("wording you would write differently… is not a mistake").
- **D2 = B (Haris):** a separate short QA look at the Builder's prose vs FACTS (summary/duty/origin), retry then code-only fallback. Built as 7.6, after Researcher QA works.
- **D3 — model and chain:** new chain **`judge`** sharing no model with `long`, so QA can never grade its own model's work. Token budget 3,000 per call (2,000 per part under plan B). Candidates tested in 7.4 (below): only GPT-OSS 120B qualified.
- **D4 — QA JSON:** `{warnings: [{id, judgement REAL|NOISE, reason}], corrections: [{field, problem, fix, source_id}], scores: {factuality, completeness, formatting_safety}}`, in that order (reasons before scores). **Code computes the status** (any 0 → REJECTED); a `status` the model writes is ignored. Code validates; one retry with the problems listed.
- **D5 = A (Haris):** QA call fails or its answer stays invalid → status **ERROR**: the run goes on, the report is produced, the phase log and a pipeline warning say "NOT reviewed by QA". QA never causes LLM_ERROR or CHECKS_FAILED on its own.
- **D6:** list numbering ("(3)", "3." at a line start) ignored by the number check before QA sees warnings (7.2).
- **D7 — testing:** offline with fake LLMs, then `scripts/eval_qa.py` live on clean and seeded cases, then the full pipeline. A false rejection counts as much as a miss (it wastes the only revision and can turn a correct answer into CHECKS_FAILED).

### What QA receives (mansha/qa.py `build_messages`)
1. **INTAKE JSON.**
2. **CHECKED BY CODE (correct; never correct these)** (`checked_facts`, 7.4): verdict, origin status (with "line excluded, no origin check" for NOT_APPLICABLE), rule of origin, duty saving status, and **what the user already gave** (shipment value; bill of materials and declaration GIVEN / NOT given or incomplete with the missing items / not needed for an excluded line; HS code).
3. **CODE WARNINGS** numbered W1, W2, … (global numbers, kept across parts).
4. **EVIDENCE** (`qa_evidence`, 7.2): candidate lines (non-chosen shortened to ID, code, description, rates), the chosen line's rule/origin/duty results, every other cited record word for word, uncited rules and passages as one line each (ID + title). Built only from what the Researcher saw (counts and percentages only).
5. **RESEARCHER JSON** (`research_for_qa`): classification reasoning step only; **without** `verdict`, step `authority`, `origin_result.status`, `origin_rule`, `estimated_saving` (code fills or verifies those exactly; 7.4, after GPT-OSS "corrected" correct values). **Since 7.6c–d** QA receives the Researcher JSON after code has unbracketed IDs and, for NOT_ELIGIBLE/NO_PREFERENCE, dropped follow-up questions and claim caveats.
- Validation (`check_qa`): exactly 3 scores, 0/1; every warning judged once (REAL/NOISE + reason), no unknown IDs; each correction names an existing field (index must exist) that is **not code-checked** and (plan B) is shown in that part, with problem, fix and an evidence ID or null; 0 ↔ corrections; REAL → factuality 0.
- Corrections reach the Researcher as "`field`: problem Fix: fix (see ID)", prefixed "QA:", in the single shared revision.
- Phase log: QA status OK / REJECTED / FAILED; scores; "Code warnings judged by QA: W1 REAL: … -> reason"; problems in QA's own answer; plan B parts. `qa_N.json` holds scores, corrections, judgements, answer problems, parts and every call.

### Plan B (7.4b, decided with Haris 17 Oct): split big reviews
- **Why:** Groq's free tier refuses a request whose prompt + answer budget exceeds 8,000 tokens (17 Oct 16:57 windows: "Limit 8000, Requested 8779"), and the router skips a model whose limit is too small. ELIGIBLE and NEEDS_MORE_DATA reports were unreviewed, i.e. half the branches. No other free model qualified (see 7.4).
- **How:** code estimates the prompt (characters ÷ 3.6; ran ~10% high vs Groq's counts). If prompt + 3,000 ≤ 7,600 → one call as before. Else: the findings first, then the steps and notes in order, packed into as few parts as fit (prompt + 2,000 ≤ 7,600 each). Each part: "REVIEW PART i/n" header, intake, CHECKED BY CODE, its own warnings (a warning goes to the part holding its field, else part 1), only the records its fields cite; part 1 also gets candidates, chosen-line tools and the uncited index; a part without the findings gets the origin basis as context only. Steps and notes appear under `items`, keyed by field name (`procedure[4]`).
- **Merge:** lowest score per metric; all corrections and judgements kept; APPROVED only if every part approves; REJECTED if any part rejects (its corrections used even if another part failed); ERROR ("NOT reviewed by QA in full") if a part failed and none rejected; > 6 parts → ERROR without calls.

## Working lessons
- Copy code with the copy button; create/edit files in VS Code, not long terminal pastes.
- **Save all (⌥⌘S) before running**; "N unsaved" means a stale run.
- **When replacing a selected block, check the lines just after it; after pasting, check indentation.**
- **Paste heredocs (`<<'EOF'`) flush left** (problem 33).
- **At the end of each step, run `git status`**: any untracked file is either committed or deleted. **Then push.**
- **A push publishes the whole history**: check for secrets in every commit before the first push.
- Two commands pasted onto one line → "illegal option"; run them one by one. Terminal text pasted into chat loses spaces; attached files don't.
- A red ✗ next to a command = non-zero exit code, not necessarily an error.
- Keep the Problems panel at zero. A newer ruff than Haris's flags ISC004 at `document_builder.py` (old code); ignore unless his ruff shows it.
- Router errors: read the attempt trail. **502 "upstream_error … 503 high demand" = provider busy; 429 "All models exhausted … reset ~Ns" = the router's cooldown (no model tried); 429 "daily_quota_exhausted … ~7m" = quota; "timeout" at ~60 s on OpenRouter = the router's per-provider timeout; 413 "Request too large… TPM: Limit 8000, Requested N" = Groq's per-request size; router log "tpm/tpd-limit" = the router's own limit check (minutes on end: a daily cap or its cooldown ladder, problem 80); 400 "Profile 'x' not found" = the chain doesn't exist. None of these is our code.**
- Router dashboard: chains are "profiles"; the toggles edit **the active chain** only. Router settings in `.env` are read only at startup. **The router keeps its own copy of each model's limits: after a provider upgrade, raise them in the dashboard too.**
- **When the router misbehaves, read its source and its database** (`server/src`, `server/data/freeapi.db`, read-only). **The `requests` table gives real tokens per call; `server_logs` (time in `created_at_ms`) explains refusals.**
- **A provider's limits page isn't the whole story** (problem 62). Test a model in `trial` before relying on it.
- **Free tiers have daily budgets and penalty ladders: plan the day's runs, and don't run multi-part cases back to back** (problems 64, 80).
- Gemini quotas and Groq daily caps reset at 04:00 Dubai. Run live checks earlier in the day.
- **Don't let new work change what a pending check tests**: put it on a branch.
- **Upgrading a limit can hide a bug the limit would have shown.**
- Tariff data: never trust aggregators. **Official Indian hosts block automated fetching**: confirm them in a browser. Official sources move: re-check links before the demo.
- **A 429 in ~0.02 s never reached a provider: it's the router's own limit check.**
- **A judge's blind spot can be systematic** (18–19 Oct): GPT-OSS catches changed facts but misses changed strength of a claim. Where a fixed rule exists, put it in code (7.6b, 7.6e, 7.8); measure the rest with the evaluation set.
- **"Works as code" ≠ "passed"** (Haris, 18 Oct), **and one clean case ≠ passed** (19 Oct): a change that affects several verdicts must run live on each of them before a merge (7.6c–e passed chargers but failed on windows/windows_nodata for new reasons).
- **Check what a rule does to every sample before shipping it** (19 Oct, 7.6e): "mandatory if it has a qualifier" alone would have silently dropped 7 notes in windows_nodata; counting verbatim notes per sample found it before any file was written.
- **QA reviewing text the user will never see only adds ways to fail** (19 Oct, problem 76): make the judge review exactly what the report shows.
- **Verbatim is only as safe as its source** (34, 79): a mandatory note printed verbatim from the Researcher's paraphrase can carry an invented fact; take fixed facts from the KB.
- **A model that ignores a correction makes the single revision worthless** (77): the safe outcome is CHECKS_FAILED; the real fix is a better model or taking the fact away from the model.
- **We started coding around free-model weaknesses on 19 Oct**: code rules that protect against any model are worth it; workarounds for one free model's quirks are a sign to change the model.
- **Buy the fix for the problem you can measure, not the one you guess** (20 Oct): the judge budget was a measured wall; the writer's quality wasn't yet proven to be the bottleneck, so only Groq was bought.
- **Competitors existing is not a reason to restart** (20 Oct): check what they really do, claim only what we can prove, and let customer evidence pick the position.
- **Derive an evaluation's answer key from code, not by hand** (17 Oct).
- Always run a "break test" on a new check; **make missing items fail by name, not by crashing** (7.6; 19 Oct: a fake LLM with one queued answer crashed when the rule was off, fixed by queuing a second).
- Print the real schema/output before writing code against it.
- A "number appears in the cited record" check proves existence, not meaning. If no agent checks a text's meaning, render it verbatim, give the model fixed meanings in code, or match by source, never by wording.
- **A filter by source only works on fields that carry a source** (52). **What an agent isn't told, it can't respect** (53).
- A substring check can be fooled by a name inside a longer name; match full names, longest first.
- **KB notes are facts for the exporter; team reminders go in `dev_notes`** (9, 37).
- When a model keeps getting a number or a fixed fact (or a format) wrong, compute or fill it in code (10, 11, 44, 75, 79). **The same for a judge: don't ask it to re-judge what code already proves** (59).
- **Give a judge the facts its rules need** (55). **Give a judge exactly what the writer saw, and only what the reader will see** (7.6, 7.6d).
- **A judge's "false rejection" can be a real catch: read it before discounting it** (59, 60; 19 Oct: every QA rejection was real).
- When the model makes the mistake the prompt invites, fix the prompt wording first (20).
- **Research before declaring a gap** (16).
- Tests catch wiring bugs, not just logic (23).
- **A fallback that always produces a correct (if plain) answer turns an outage into a degraded demo instead of a broken one.** The same holds for QA: ERROR → report still produced, honestly marked "NOT reviewed by QA".
- A retry that hits a cooldown is wasted (8.6b). A fast provider-busy failure shouldn't use up the only retry (43).
- **Totals can leak individual values** (49).
- **Read the reports, not just OK/FALLBACK or the report check**: most problems from 30 to 79 passed every automatic check and were found by reading.
- **A code check on the finished output catches forms of mistakes in milliseconds; it can't judge meaning** (report check, 9.6b).
- f-strings: no same-type quotes nested inside an f-string before Python 3.12; avoid them anyway.
